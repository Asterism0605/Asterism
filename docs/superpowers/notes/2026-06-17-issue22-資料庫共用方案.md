# Issue #22 資料庫共用方案討論（2026-06-17）

> 用途：跟組員拍板「外部圖池（images 表）怎麼共用、怎麼上線」。
> 前提：**以正式上線為基準**做決定。分支 `demo/image-spread`。
> 相關：見同日 `2026-06-17-issue22-組員討論-延展流程與圖庫部署.md` 第 4 節。

---

## 0. 現況與問題

- 外部圖池目前在我本機：`DATABASE_URL = postgresql://localhost:5432/asterism_demo`，共 **239 筆**。
- 組員 `git pull` 下來連的是**自己空的 DB** → 看不到這 239 張；`localhost` 也**無法部署**。
- **關鍵釐清**：DB 只存 metadata（`url` + 分類），**圖片檔本身在 Pexels / Unsplash CDN**，我們不存圖。
  → 要共用的只是「分類資料」，不是幾 GB 的圖，**不需要圖床**。

---

## 1. 先破除一個誤區：「每個人自己建一個本機 DB」不能當上線方案

- `localhost` 的 DB 只有自己連得到。站台一旦部署到線上，伺服器要連的是一個
  **有公開位址、託管在某處的 DB**；本機 DB 部署後就是空的、連不到。
- 所以「各自本機 DB」最多只能當**開發期各自的環境**，**無法成為 production 的資料庫**。
- 結論：**只要要上線，雲端（託管）Postgres 就跑不掉。**
  真正要決定的不是「雲端 vs 本機」，而是 **資料的「真相來源」放哪、開幾個 DB 實例**。

---

## 2. 關鍵性質：圖池是「唯讀參考資料」

- 線上使用者**不會寫入** images 表（他們只是瀏覽延展）。
- 真正會寫它的只有**我離線跑 CLIP 加工的時候**（分類、標 `needs_review`、刪圖、養大圖池）。
- 這個性質讓最穩的模式是「加工廠 / 真相來源 / 對外副本」三層分離（見第 4 節）。

---

## 3. 方案比較

| 方案                     | 做法                                 | 優點                                          | 缺點                                           | 能上線？       |
| ------------------------ | ------------------------------------ | --------------------------------------------- | ---------------------------------------------- | -------------- |
| **A. 各自本機 DB**       | 每人本機各建一個，靠 seed 檔灌資料   | 開發離線、互不干擾                            | **無法當 prod DB**；資料易漂移；每次改動要重灌 | ❌（單獨不行） |
| **B. 共用雲端 Postgres** | 開一個 Supabase / Neon，大家連同一個 | 真正共用、review 刪圖即時同步、**可直接部署** | 要管連線字串（密鑰）、依賴網路                 | ✅             |
| **C. SQL dump 互傳**     | `pg_dump` 出檔，組員 `psql` 灌進本機 | 不用雲端                                      | 只是快照、要手動同步；一樣不能當 prod          | ❌（單獨不行） |

> 239 筆 metadata 極小，Supabase / Neon **免費額度綽綽有餘**。

---

## 4. 建議架構：雲端 Postgres + seed 檔當真相來源

```
我的本機 DB（加工廠：跑 CLIP、標 needs_review、刪圖、養大圖池）
        │  匯出
        ▼
  committed seed 檔（進 git，當「真相來源 source of truth」）
        │  seed / 灌入
        ▼
  雲端 prod DB  ← 部署的站台連這個
        └─（組員開發：要嘛連雲端，要嘛本機從同一份 seed 檔灌）
```

- **DB 是我私人的加工廠**：CLIP 分類、review、刪圖都在本機跑。
- **git 裡的 seed 檔是真相來源**：三個環境（我本機、組員本機、prod）都從同一份灌，保證一致、可重現。
- **雲端是上線時對外服務的副本**。

---

## 5. 上線版具體配置（建議步驟）

1. **現在～開發期**：開 1 個雲端 Postgres（**Supabase 或 Neon** 二選一），大家共用。
   - 連線字串放 `.env`（**不要 commit**），`.env.example` 只留範本欄位。
2. **接近上線**：再開**第二個**雲端實例當 production，**dev / prod 分開**，
   避免開發期的實驗污染正式資料。
3. **可重現性**：把 `images_dump.json`（已存在，239 筆）或 `pg_dump` 的 seed 檔
   commit 進 git；新環境都從同一份灌。
4. **匯出前**：先 review 那 **60 張 `needs_review`**、刪掉不要的，**再** `pg_dump` 備份 + 匯出，
   避免共用到還沒整理的版本。

---

## 6. 一個更精簡的替代：prod 直接出靜態 JSON（要一起考慮）

- 因為圖池是**唯讀**，最精簡的上線法是**把資料當靜態 JSON 隨前端一起出**——
  組員 PR #49 的 `image.service.ts` 本來就是純讀本地 JSON、沒接 DB。
- **要不要保留 DB 服務層（Express API + 雲端 DB），取決於之後想不想要**：
  分頁 / 篩選 / 圖庫持續長大 → 保留雲端 DB；**純展示固定圖池** → JSON 就夠，連 prod DB 都省。
